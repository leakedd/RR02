## Correctif latence (même jour) — daemon **v33** = nouvelle référence

**Symptôme rapporté** : des joueurs visibles en jeu n'apparaissaient sur le radar qu'avec un gros retard.
**Cause** : les *positions* étaient relues toutes les 1 s, mais la **liste des objets** n'était reconstruite qu'à chaque re-scan complet — or le scan durait 5–90 s → un joueur fraîchement connecté n'entrait dans la liste qu'après ce délai.

**Mesures** (`src/bench_scan.cpp`) : 95 000 régions RW = **22,1 Go**.

| Mode | Durée | Débit |
|---|---|---|
| 1 thread | 8,5 s | 2,7 Go/s |
| 4 threads | 2,3 s | 9,8 Go/s |
| 8 threads | 2,4 s | 9,4 Go/s |
| 12 threads | 2,0 s | 11,3 Go/s |

**Où vivent les joueurs** (`src/bploc.cpp`) : les BasePlayer validés tiennent dans **24 régions = 0,12 Go** ; toutes les régions contenant des *candidats* = **182 régions = 0,80 Go** (sur 22 Go).

**Architecture v33** :
- **scan parallèle** (`par()`, 6-8 threads) : tout le RW en ~5 s au lieu de 60-90 s ;
- **passe chaude** toutes les ~0,25 s sur les seules régions candidates (~0,8 Go → **85-170 ms**) → les nouveaux objets sont détectés en < 1 s ;
- **passe complète** toutes les 10 s : filet de sécurité (couvre une entité apparue dans une région encore inconnue) + rafraîchit la liste des régions chaudes ;
- **écriture JSON toutes les 0,5 s** (`ts` en secondes fractionnaires pour un âge exploitable) ;
- **fusion + élagage** au lieu du remplacement : la passe complète peut *rater* des entités vues par les passes chaudes → on unit puis on élague ce qui ne valide plus (`+0x328 → PlayerModel` + flags lisibles) ;
- validation renforcée à la découverte : `+0x328 → PlayerModel` **et** position saine **et** flags lisibles (élimine les objets transitoires).

**Latence bout-en-bout mesurée** : âge JSON min 0,02 s / moy 0,28 s / max 0,50 s ; découverte 85-172 ms ; poll overlay 0,4 s → **≤ ~1,1 s au total** (contre jusqu'à 90 s avant).

**Lancement** : `./radar_v33 [threads] [periodeComplete_s] [periodeEcriture_s]` → défaut utile : `./radar_v33 6 10 0.5` (lancé sous `nice -n 5`).

### Pièges rencontrés (v33)
- **`binary_search` sur un vecteur non trié** : la fusion des passes chaudes ajoutait les nouveaux éléments en fin de vecteur → le test `binary_search` échouait → **doublons en masse** (le radar affichait 188 entités pour ~68 réelles). Toujours trier + `unique` après une fusion.
- **Passe complète qui *remplace*** la liste : elle peut trouver *moins* d'entités que les passes chaudes (lectures mémoire sur 5 s pendant que le jeu mute) → ne jamais remplacer, fusionner puis élaguer.
- Objets transitoires (mémoire en cours d'écriture par le jeu) : ils passent parfois la validation un court instant puis disparaissent → filtrés par la validation position/flags, jamais affichés.

## Calque « items au sol » — daemon **v34** = nouvelle référence (même jour, nuit)

**Demande** : voir les objets lâchés au sol (armes, ressources…) sur le radar. Périmètre = radar seul (pas d'ESP).

### Livrable vérifié
Overlay : **couche items** (carrés 6×6 à contour sombre 8×8, couleur par catégorie, libellé du shortname au zoom ≥ 2,6, touche **I** pour masquer/afficher, clic = ancre + nom).
Live constaté : **67 joueurs (7 en ligne / 60 endormis)** + **9 à 16 items nommés** (`arrow.wooden`, `scrap`, `metalblade`, `pants`, `tool.binoculars`, `sleepingbag`, `workbench.upgrade.recyclebin`, `rock`, `diving.mask`, `mask.bandana`, `pants.shorts`, `seed.hemp`, `siegetower`), âge JSON **0,28 s**.

### Position monde — deux chemins (⚠️ le `Bounds`/`+0x118` est LOCAL préfab = zéro)
```
PAT B (joueurs, exact 0,000 m) : BaseEntity+0x1B8 -> Model ; Model+0x28 -> Transform IL2CPP
                                 ; +0x10 -> Transform natif ; nat+0x28 -> struct ; +0x90 = Vector3
PAT A (universel, ~0,3 m d'écart) : r64(obj+0x90) -> r64(+0x00) -> floats à +0x90
```
PAT A marche sur `DroppedItem`, `PlayerCorpse`, caisses, caches, supply — c'est le **test de validité générique** pour toute classe sans champ discriminant.
Le tableau de Transform natif a un **pas de 32 octets** `[position | quaternion | échelle]`, positions consécutives espacées de **0x20**. `TransformHandle.pTransformData` lu *comme objet* (`+0x90` dedans) = garbage → l'indirection correcte est `r64(h+0)` puis `+0x90`.

### Test d'instance : le pointeur de klass en tête ne suffit PAS
Un balayage de « valeur == klass » renvoie surtout des **métadonnées** (tables de types, descripteurs) : 564 candidats `DroppedItem` → **0 vraie instance** avec le seul test d'en-tête. Il faut un champ propre à la classe pointant vers un type propre à la classe :

| Classe | Test fort |
|---|---|
| `BasePlayer` | `r64(o+0x328)` → objet de klass `PlayerModel` |
| `DroppedItem` | `r64(o+0x210)` → objet de klass `GameObjectRef` |
| caisses / caches / cadavres | test PAT A (position saine) |

Résultat : 564 → **72 items réels**, groupés autour de la position du joueur ; les **prefabs** (positions fixes lointaines, dupliquées) tombent naturellement.
**Comparer les NOMS de klass, pas les adresses** : `r64(o+0x208) == adresse(Item)` échouait là où `nom_klass(...) == "%842e6b2f…"` réussissait.

### Noms d'items
```
DroppedItem+0x208 -> Item ; Item+0xD8 -> ItemDefinition ; ItemDefinition+0x28 -> shortname
```
* l'`ItemDefinition` est localisé **par nom de klass** dans les champs de l'`Item` (0x10..0x2F8) — la disposition live de `Item` ne colle pas au dump, donc on localise, on ne fige pas l'offset ;
* shortname accepté seulement si `^[a-z0-9._-]{2,48}$` (rejette les chaînes de métadonnées type `duleSeating`) ;
* un champ frère illisible (`ItemDefinition.itemid` à `+0x20` renvoyait 963906841) n'invalide pas l'objet : on juge sur le champ plausible.

### 🔴 Piège majeur : les chaînes IL2CPP sont en **UTF-16**
`klass@+0x00 / monitor@+0x08 / int32 length@+0x10 / uint16 chars[]@+0x14` (UTF-16LE).
Une lecture **octet par octet** s'arrête sur le `0x00` du 2ᵉ octet : `"rifle.ak"` → `"r"`, `"ammo.rifle"` → `"a"`. J'ai perdu plusieurs passes à chercher « le bon champ » alors que le champ était bon.
**Ne pas unifier les décodeurs** : le nom de klass est un `const char*` natif à `klass+0x10` (octets, NUL) — celui-là reste octet.

### Autre piège (pipeline)
`serve.py` reconstruisait le JSON avec une **liste de clés explicite** → la clé `items` était silencieusement jetée : le daemon écrivait les items, le navigateur ne les voyait jamais. Toujours vérifier **l'endpoint servi** (`curl localhost:8789/radar.json`), pas seulement le fichier sur disque.
